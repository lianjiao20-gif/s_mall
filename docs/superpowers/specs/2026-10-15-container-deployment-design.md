# 腾讯云单机容器部署设计

## 目标与范围

把现有拾间电商案例部署到一台腾讯云 Linux 服务器，供接口和 UI 自动化练习使用。前端、后端、MySQL 均在 Docker 容器中运行。用户尚未提供实例类型、系统、公网 IP、SSH 方式或域名；这些信息只影响最终的服务器操作和站点地址，不进入仓库配置。

项目仍使用演示账号、固定商品和模拟支付，不接入真实支付或发货。部署过程不得执行会清除订单的 `db:reset`。

## 方案选择

采用单机 Docker Compose 管理三个服务：Caddy、Node.js API、MySQL。Caddy 容器存放 React 的 Vite 构建产物，提供 SPA 页面，并把 `/api/*` 原路径转发到 API 容器。Node.js 容器只运行编译后的 JavaScript。MySQL 使用命名卷保存数据。仅 Caddy 映射宿主机网站端口；API 和数据库只通过 Compose 内部网络访问。

相比 Nginx 容器，Caddy 在有域名且 DNS 指向服务器时可自动申请和续期 HTTPS 证书；相比在宿主机安装反向代理，所有应用服务均可随 Compose 一起管理。没有域名时使用明确的 HTTP 站点地址和 80 端口，不依赖自签名证书。

## 仓库交付物

- 为 API 提供多阶段 Dockerfile：构建 TypeScript，最终镜像只含运行依赖、`dist` 和数据库 schema。运行入口为 `node dist/server.js`；初始化入口为 `node dist/seed.js`。
- 为前端提供多阶段 Dockerfile：构建 Vite 静态资源，最终由 Caddy 容器提供。Caddy 配置支持 SPA 路由回退和 `/api/*` 转发。
- 新增独立的生产 Compose 配置，不改变现有本地开发 `compose.yaml` 的使用方式。三个服务设置合适的健康检查与重启策略，MySQL 使用命名卷；数据库就绪后才启动 API。
- 提供不含真实凭据的部署环境变量示例，至少包含数据库名、用户、密码、root 密码、JWT 密钥和站点地址。实际配置文件不提交到 Git。避免把演示用的默认数据库密码和 JWT 密钥用于服务器。
- README 增加构建、首次启动、幂等初始化、更新、日志、停机和验收步骤；明确 `db:reset` 会删除业务数据。

## 数据与启动流程

首次部署：配置环境变量，构建镜像，启动数据库和 API，执行一次幂等的 `seed`，再检查网页与接口。由于 API 当前启动时要求数据库可连接，但 schema 可在 API 启动之后创建，初始化命令可以在 API 镜像中作为一次性任务运行。`seed` 重复执行不会覆盖已有库存、购物车或订单。更新版本时重建前端和 API 镜像并重启相关容器，保留 MySQL 卷，不自动重置数据。

站点地址由部署变量设置。有域名时，域名 DNS 指向公网 IP，Caddy 对外使用 80/443；无域名时以 HTTP 和公网 IP 访问。腾讯云防火墙或安全组需允许所用网站端口，SSH 端口按服务器现有配置保留。域名和证书配置以最终服务器信息为准。

## 验收与边界

本地先验证镜像构建和 Compose 配置，再在服务器验证：首页及前端深链接可访问，`GET /api/health` 返回 `ok`，Swagger 页面可打开，演示账号可登录，商品列表、购物车和模拟下单流程可用；重启容器后订单仍存在。上线后记录实际访问地址和启动状态。

服务器登录信息、系统版本、公网 IP 和域名尚未提供，因此远程上传、端口放通、DNS、HTTPS 和线上验收必须等这些信息到位。SSH 密码和私钥内容不得写入仓库或聊天记录。
